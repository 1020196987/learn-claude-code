# 收尾 · 20 章共通的设计哲学

> 学完 20 章后，回头看 harness 工程的共通思维。

## 1. 循环不变，机制叠加

整个仓库最重要的设计哲学是**循环始终不变**。从 s01 到 s20，agent loop 始终是同一个骨架：

```python
while True:
    response = LLM(messages, tools)
    if not has_tool_use(response.content):
        return
    results = execute_tools(response.content)
    messages.append(tool_results)
```

变化的是循环**周围**的机制：

- 工具分发（s02）：dispatch 表替代硬编码
- 权限（s03）：执行前插入判断
- 钩子（s04）：把硬编码搬到注册表
- 计划（s05）：给模型一个 plan 工具
- 子 agent（s06）：递归地复用同一个循环
- 技能（s07）：system prompt 外部化
- 压缩（s08）：循环开头加预处理
- 记忆（s09）：跨会话的持久层
- prompt 组装（s10）：运行时拼接替代硬编码
- 错误恢复（s11）：循环不崩
- 任务系统（s12）：文件系统做任务图
- 后台（s13）：daemon 线程 + 通知
- 调度（s14）：独立线程 + 队列
- 团队（s15）：Lead + 队友线程 + 文件收件箱
- 协议（s16）：request_id + 状态机
- 自治（s17）：idle 轮询 + 自动认领
- worktree（s18）：目录隔离
- MCP（s19）：外部工具协议
- 综合（s20）：合回一个循环

每加一层机制，**循环本身只多了几行**——很多时候是 1-3 行。这就是好的扩展设计：**核心稳定，外围叠加**。

## 2. 三类分离原则

回顾 20 章，可以提炼出三类贯穿始终的分离原则：

### 2.1 决策与执行分离

模型负责决策（要不要调工具、调哪个、参数是什么）；harness 负责执行（调了就跑、结果喂回去）。

这在每一章都有体现：

- s01：循环决定何时退出，代码决定如何执行
- s03：模型不判断"该不该做"，代码判断"能不能做"
- s05：模型列计划，代码不替它列
- s08：模型不知道有压缩存在
- s19：模型不知道工具来自哪里

### 2.2 上下文与状态分离

LLM 没有持久状态。所有"记忆"都是 harness 在维护：

- s07：技能内容在文件系统，不在 prompt
- s08：旧 tool_result 在文件里占位，不丢
- s09：偏好跨会话保存，靠文件系统
- s12：任务图持久化，跨进程可恢复
- s14：cron job 持久化，重启不丢

**核心模式**：状态在文件系统，模型只看到当前窗口的内容。

### 2.3 机制与业务分离

s04 的 hooks 把"扩展点"从循环里拆出来。s10 的 section 把"prompt 内容"从硬编码里拆出来。s16 的协议把"协调逻辑"从消息内容里拆出来。s19 的 MCP 把"工具实现"从循环里拆出来。

**核心模式**：机制提供"如何做"，业务定义"做什么"。

## 3. 便宜的先跑，贵的后跑

贯穿 s08（压缩管线）、s11（错误恢复）的设计原则：

```
0 API 调用：
  - L1 snip_compact (消息数)
  - L2 micro_compact (旧 tool_result 占位)
  - L3 tool_result_budget (大结果落盘)

1 API 调用：
  - L4 compact_history (LLM 摘要)

应急：
  - reactive_compact (prompt_too_long 时)
```

**便宜的先跑**是因为：

1. 不消耗 API 调用（省钱）
2. 不引入 LLM 理解偏差（更可控）
3. 90% 的情况 L1-L3 就够了

**贵的后跑**是因为 LLM 摘要有损（丢失细节）、有成本（一次 API 调用）、有不确定性（不同次摘要质量不同）。能避免就避免。

## 4. 路径粒度：粗 vs 细

仓库在不同层面给出了"粗"和"细"两种实现的对比：

### 4.1 粗实现 vs 细实现

| 机制 | 粗（教学版） | 细（CC 源码） |
|------|------------|-------------|
| TodoWrite reminder | 3 轮未调用就提醒 | 3 个 todo 全 completed 但缺 verification 项时 nudge |
| Task ID 生成 | timestamp + random hex | 顺序 ID + highwatermark 防重用 |
| Cron 触发 | 直接入队 | 抖动防惊群 + 优先级 + 过期 |
| 错误重试 | 简单 try/except | 十几种 reason/transition + 流式暂扣 |
| 后台通知 | 内存字典 | 通知队列 + 优先级 + 流式处理 |
| Worktree | `.worktrees/` 简单目录 | `.claude/worktrees/` + 持久化 state + default branch 检测 |

**教学版的粗实现不是缺陷**——它服务于"理解核心机制"的目标。生产版的细实现是为了"在边界条件下也正确"。

### 4.2 何时用粗实现？

- 学习阶段
- MVP / 原型
- 单一用户、单一会话、低并发
- 任务量小、不需要容错

### 4.3 何时用细实现？

- 多用户、多会话
- 高并发（多人同时用）
- 长期运行（数天不重启）
- 关键任务（不能丢消息、不能死锁）
- 安全敏感（权限隔离要严谨）

## 5. 文件系统作为通用基础设施

20 章里反复出现"用文件系统做 XXX"的模式：

| 用途 | 章节 | 路径 |
|------|------|------|
| Skill 内容 | s07 | `skills/*/SKILL.md` |
| Memory | s09 | `.memory/*.md` + `MEMORY.md` |
| Task 图 | s12 | `.tasks/*.json` |
| Cron job | s14 | `.scheduled_tasks.json` |
| Team 收件箱 | s15 | `.mailboxes/*.jsonl` |
| Worktree | s18 | `.worktrees/*` + `events.jsonl` |
| MCP transcript | s08 | `.transcripts/*.jsonl` |
| 工具落盘结果 | s08 | `.task_outputs/tool-results/*` |

**为什么是文件系统**？

- **可见性**：人类可以直接 cat/ls 排查
- **可恢复性**：进程崩溃不丢
- **跨进程通信**：天然共享
- **可观察性**：事件日志天然存在
- **调试友好**：出错时可以手动修改

CC 在文件之上加了文件锁（`proper-lockfile`）和并发安全，但在底层仍然是文件系统。

## 6. 模型与 Harness 的边界

整个仓库反复示范的边界划分：

**模型做（不要让 harness 抢）**：
- 决定下一步做什么
- 判断什么时候工具返回是"成功"
- 选择用什么工具、什么参数
- 解读工具输出
- 列计划、生成摘要
- 解释、归纳、抽象

**Harness 做（不要让模型操心）**：
- 把工具调用排队、执行、收集结果
- 检查权限、记录日志
- 压缩上下文、加载记忆
- 调度任务、后台执行
- 通信队友、协调开关
- 错误恢复、重试、降级
- 缓存、序列化、prompt 组装

**判断标准**：如果模型能做得更好，就让模型做；如果 harness 能做得更可靠，就让 harness 做。两可之间，倾向于 harness 做（更可控、更可测试、更可调试）。

## 7. 给自己做 harness 的几条建议

如果你想给自己领域造一个 agent harness（比如酒店运营、医疗研究、农田管理），从这 20 章拿走这些建议：

### 7.1 先建循环，再加机制

从 `while True` 开始。验证 LLM 能干这件事之后，再决定要不要加 hooks、压缩、记忆等。如果你的领域模型足够强、上下文足够大，你可能根本不需要 s08 之后的章节。

### 7.2 dispatch 表是你的好朋友

所有"加新工具 = 加一行"的扩展性都来自 dispatch map。**用字典查表替代硬编码 if/elif**。这是 s02 教的最重要的一招。

### 7.3 让模型说"我需要什么"，而不是你猜

s07 的技能加载、s09 的记忆加载，都是这个原则：

- 不要把"模型可能需要的所有东西"塞进 prompt
- 让模型看到一个**目录**（轻量）
- 让模型主动**请求**完整内容（按需）

这条原则比看起来重要——它直接决定了 token 成本和模型注意力分配。

### 7.4 错误是常态，不是异常

s11 的核心洞见：**生产环境的 harness 必须把错误当作正常事件**。429、529、prompt_too_long 每天都会发生。一个"一碰就崩"的 harness 不能用。

### 7.5 持久化靠文件系统

任务、记忆、技能、cron job、team config——一切需要"Agent 重启后还在"的东西，都放在文件系统。**别放内存**。

### 7.6 异步是基本的

Agent 不是"请求-响应"，是"长期运行"。s13 的后台、s14 的 cron、s15 的队友线程、s17 的 idle 轮询——这些都不是特殊场景，是**任何长期运行的 agent 都需要的能力**。

### 7.7 权限是基础安全

s03 的三道闸门是最小权限模型。生产环境还会有：用户身份、token 范围、操作审计、撤销机制。但起点是：**执行前做判断**。

### 8.3 思考题

1. **如果模型没那么强**，harness 应该怎么调整？（提示：补偿性设计——更强的规划、更长的 TodoWrite、更多的权限检查、更激进的压缩）
2. **如果上下文窗口变成 10M token**，哪些章节可以删？（提示：压缩、子 agent、记忆都可能弱化）
3. **如果 agent 要在断网环境下工作**，哪些章节必须改？（提示：MCP、子 agent 异步路径、远程队友）
4. **如果 agent 要给 1000 个并发用户服务**，哪些章节的并发模型要重新设计？（提示：任务锁、文件锁、收件箱、worktree）
5. **如果要让 agent 自己学习新工具**（不是写死工具定义），harness 应该加什么机制？（提示：MCP 已经是答案的一半，另一半是 skill auto-loading）

## 9. 终极反思

回到仓库的中心论点：

> **Agency 来自模型。Agent 产品 = 模型 + Harness。**

学完 20 章你应该能感受到：**harness 决定了 agent 的天花板**。同一个 Claude 模型：

- 配上 s01 的循环 = 一个能调 bash 的玩具
- 配上 s05 的 TodoWrite = 一个能完成多步任务的初级助手
- 配上 s08 的压缩 = 一个能长时间工作的工程师
- 配上 s15 的团队 = 一个能协调多人的项目经理
- 配上 s19 的 MCP = 一个能接入任何外部系统的万能接口

**模型是固定的（同一个 Claude），能力差异完全来自 harness**。

这就是 harness 工程的意义——你不是在写智能，你是在**为智能搭建栖居的世界**。世界的质量——agent 能看得多清楚、行动得多精准、可用知识有多丰富——直接决定了智能能多有效地表达自己。

造好 Harness。Agent 会完成剩下的。
